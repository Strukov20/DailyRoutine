## What was built

### Security regression guard (`supabase/tests/130_security_regression_test.sql`)

The anon-EXECUTE-grant finding recurred three times (Phase 3: two invitation RPCs; Phase 5:
`set_task_assignment`; Phase 6: `enqueue_task_assignment_notification`, `backoff_interval`)
with no automated test for the *general* invariant ever existing — each time caught only by a
one-off manual `pg_proc`/`has_function_privilege` query. Built as a schema-driven check
(queries `pg_proc`/`pg_namespace` directly, never a hardcoded function list — per the brief's
own explicit "don't build a fragile grant snapshot" instruction) asserting: anon/PUBLIC may
`EXECUTE` a function in `public`/`notifications` only if it's a trigger function (Postgres
itself refuses to invoke a `returns trigger` function outside a trigger context, regardless of
any grant — confirmed directly by querying the real SQLSTATE, `0A000`, and asserting against
it in the test rather than just asserting the exemption in prose) or is in a short reviewed
whitelist (currently one entry, `current_profile_id()` — a harmless `select auth.uid()`
wrapper, not `SECURITY DEFINER`, no side effects). The `notifications` schema gets a stricter
rule: zero EXECUTE for anon/authenticated/PUBLIC on anything at all, trigger functions
included, no whitelist.

**Verified the guard actually catches a regression, not just documents one**: temporarily
re-granted `anon` `EXECUTE` on a real function (`notification_preference_enabled`), re-ran
just this test file, confirmed it failed with the expected assertion (`have: 1, want: 0`),
reverted the grant, confirmed it passed again. This is recorded as its own testing-strategy
convention (see the wiki page) since it's a real, generally-applicable lesson, not specific to
this one test.

6 new pgTAP assertions; 299/299 total (293 existing + 6 new) pass against a real local
instance after a fresh `db reset`.

### Secret/bundle audit, specifically for `NOTIFICATION_WORKER_SECRET`

Confirmed via `grep` that this secret is referenced in exactly one place in the entire
codebase: `Deno.env.get("NOTIFICATION_WORKER_SECRET")` inside
`dispatch-notifications/index.ts` — never in any client-side file, never `.env.example`, never
an `EXPO_PUBLIC_*` name. Ran a fresh `expo export` for both platforms and scanned the compiled
Hermes bytecode (`strings ... | grep`) plus the public Expo config for
`NOTIFICATION_WORKER_SECRET`/`SERVICE_ROLE`/`CLIENT_SECRET` — clean on all three surfaces.
This specific secret had not been scanned for by name in any prior phase's audit (Phase 6's
own scan checked for `SERVICE_ROLE`/OAuth secrets, not this one by name), so this closes a
real (if narrow) gap in prior verification coverage, not just repeats it.

content (as opposed to `DECISIONS.md`'s historical rationale or `ARCHITECTURE.md`'s design).

instruction), the repeatable secret-audit commands, and an explicit "Known limitations"
section listing exactly what remains unverified and why.

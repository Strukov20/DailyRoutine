## Role

Lead software architect and senior React Native engineer responsible for building a
production-quality mobile application.

## Product

Working product name: **FamilyFlow**

FamilyFlow is a personal and family planner for iOS and Android.

Its purpose is to help individuals and families understand:

- what needs to be done;
- when it needs to be done;
- who is responsible;
- whether family schedules contain conflicts.

This is not just a to-do list. It combines:

- personal tasks;
- calendar events;
- reminders;
- family calendars;
- shared responsibilities;
- child schedules;
- future AI-assisted planning.

The working name must be stored centrally so it can be renamed later without a large
refactor.

## Technology direction

Use: React Native; Expo; TypeScript with strict mode; Expo Router; Supabase for PostgreSQL,
authentication, realtime sync, storage, and backend capabilities; TanStack Query for
server-state management; Zustand only for small client-side UI state; React Hook Form; Zod
validation; React Native Paper with centralized custom design tokens; Expo Notifications;
Expo Localization with i18next; Jest or Vitest, depending on current Expo compatibility;
React Native Testing Library; Maestro for future mobile E2E tests; ESLint; Prettier; GitHub
Actions.

Before choosing versions, check current Expo compatibility and use mutually compatible
stable versions. Do not use deprecated packages or APIs.

Support Ukrainian and English localization from the beginning. Do not hardcode user-facing
strings directly inside components.

## Git rules

The repository will use: `main` for stable code; `develop` for integration; short-lived
`feature/*` branches.

Before modifying anything:

1. Inspect the repository.
2. Run `git status`.
3. Preserve any existing user changes.
4. If the repository is not empty, analyze the current project before making changes.
5. Do not push anything.
6. Do not merge into `main`.
7. Local commits are allowed only when the working tree was clean before your work.
8. Use clear conventional commit messages.

Never commit: secrets; `.env` files; API keys; signing certificates; generated build
artifacts.

Provide `.env.example`.

## Core product model

The application has two connected modes.

### Personal planner

Each adult user has a personal planner containing: Today; Tomorrow; Inbox; tasks with or
without a scheduled time; calendar events; reminders; recurring tasks; categories;
priorities; private or family-visible items.

### Family planner

Users can create a Family Space and invite other adults.

A family contains: Owner; Adult members; Child profiles.

A child does not need an account. Parents manage the child's calendar. The architecture must
allow a child profile to be linked to a real account in the future.

Family members can see: the combined family schedule; shared family tasks; child events;
responsibilities; assignments; sanitized busy blocks for private events.

A user may eventually belong to multiple families, even if the initial UI focuses on one
active family.

## Critical domain rule

An event and a responsibility are not the same thing.

Example:

Event: Swimming; Child: Son; 17:00–18:00.

Responsibilities: Drop off → Mom; Pick up → Dad.

Model events and responsibilities separately. Do not implement child pickup/drop-off as
ordinary text fields on an event.

## Task structure

A task may contain: title; description; date; start time; duration; one or more reminders;
priority; category; assignee; recurrence; visibility; completion status; assignment status.

Only the title is mandatory.

Tasks can be: personal; shared with family; assigned to a family member; unassigned; claimed
using "Take task"; scheduled for a date and time; scheduled for a date without a time; kept
in Inbox without a date.

Priorities: Normal; Important; Critical.

Default categories: Work; Family; Home; Shopping; Health; Other.

Users must be able to add custom categories later.

## Assignment workflow

When one adult assigns an appropriate task to another adult: the recipient is notified; the
assignment can require Accept or Decline; its status must be represented explicitly;
assignment history must remain auditable.

Do not assume that assigning a task always means automatic acceptance.

## Privacy

Personal items support: Private; Family.

For a private event, family members may see: owner; start time; end time; "Busy."

They must not see: title; description; category; notes; attachments; other private
metadata.

The data architecture must prevent private details from leaking through direct API queries,
realtime events, logs, notifications, or client-side filtering.

Do not solve privacy only by hiding fields in the UI. Design proper Supabase Row Level
Security and a sanitized availability mechanism, view, or secure RPC.

Document the proposed security approach before implementing database migrations.

## MVP navigation

The main mobile navigation should contain: Today; Calendar; Inbox; Family; Profile.

Task creation must be accessible from primary screens using a clear create action.

The initial application shell should include: authentication entry point; onboarding
placeholder; bottom navigation; Today screen; Calendar screen; Inbox screen; Family screen;
Profile screen; reusable empty states; loading states; error states; light and dark themes;
Ukrainian and English localization.

The interface should feel modern, calm, and suitable for daily use. Prioritize clarity,
readable typography, generous spacing, and accessibility over decorative complexity.

## MVP success scenario

The MVP is successful when:

1. Two adults install the application.
2. Each adult creates an account.
3. One adult creates a family.
4. The second adult joins the family.
5. They create a child profile.
6. Each adult maintains personal tasks and events.
7. Private events appear to the family only as Busy.
8. They see a combined Family Today schedule.
9. They create and assign shared tasks.
10. They create a child event.
11. Drop-off and pickup responsibilities are assigned separately.
12. Changes synchronize between both devices.
13. Relevant reminders and assignment notifications are delivered.

## Roadmap boundaries

### MVP

Focus on: account and authentication; personal tasks; Inbox; Today and Tomorrow; task
scheduling; reminders; recurring tasks; personal calendar; Family Space; adult invitations;
child profiles; shared family calendar; shared tasks; task assignment; Take task; privacy;
child events; drop-off and pickup responsibilities; Family Today.

### V2 — do not implement now

Document architectural support for: Google Calendar integration; Apple Calendar integration;
Week and Month calendar views; conflict detection; subtasks; attachments; shared shopping
lists; widgets; comments; advanced offline sync; statistics.

### V3 — do not implement now

Document architectural support for: natural-language task creation; Plan My Day; AI
scheduling; automatic rescheduling with user confirmation; family conflict resolution; AI
family planning.

AI must eventually act as a planning engine, not merely as a chat interface.

## Offline behavior

For MVP, provide: cached read access to recently loaded data; clear offline state; safe
retries; optimistic updates only where rollback is reliable.

Do not claim full offline-first synchronization unless it is actually implemented and
tested.

Document conflict-resolution rules for future advanced offline sync.
